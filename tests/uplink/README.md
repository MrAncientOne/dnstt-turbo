# Production-stack uplink simulations

Run from the repository root with Go and Python 3 available:

```sh
python3 tests/uplink/run.py --mode both
python3 tests/uplink/run.py --mode performance --case fast-500m --repeat 3
python3 tests/uplink/run.py --mode both --case tls-during-bulk --soak-seconds 60
python3 tests/uplink/run.py --mode performance --case fast-500m --size-mb 64 --profile
```

`--profile` runs only the production-stack transfer and captures CPU, heap, blocking and mutex profiles, plus text reports when pprof is available. Profiling adds overhead; compare unprofiled runs for throughput. Raw-carrier tests are excluded from profiles. `--size-mb` overrides bulk size to reduce startup bias; large slow-link transfers can exceed the 60-second per-stream deadline. `PPROF_BIN` selects an installed report tool. If Go omits the pprof binary but includes its source, the runner builds it locally; otherwise retain the raw files for another host.

`--protocol-only` skips the raw-carrier calibration while retaining protocol transfers and carrier correctness checks. `fast-slow-fast-upload` transfers 64 MiB in upload/download/upload order while uplink capacity falls from 500 Mbps to 5 Mbps at three seconds, then returns at fifteen seconds. It checks completion and final upload recovery; the separate controller test checks admission-shaper hysteresis directly.

The runner defaults to offline Go dependency resolution. Populate the Go module cache first on a connected machine, or explicitly set `GOPROXY`. `GO_BIN`, `GOMODCACHE`, and `GOCACHE` can select an installed toolchain and writable caches. `GO_BIN` accepts an executable name on `PATH` (such as `go`) or an absolute/relative executable path; relative paths are resolved from the directory where you invoke the runner. Without `GO_BIN`, the runner finds `go` on `PATH`. Use `--output` to retain artifacts in a chosen directory. Avoid competing CPU-heavy jobs while measuring performance.

`prepare.py` freezes production sources into an isolated module, records input source hashes, and replaces OS listener/backend dial seams with pipes. It also gives each peer its own startup packet-queue size: twice the client's adaptive maximum window (or static window when adaptation is off), and twice the server's configured window. Fixture-only constructors isolate these settings because the peers share one test process; deployed peers have separate startup globals. Earlier artifacts used a shared 2048-packet setting and could incur additional internal queue drops on fast paths. The test runs the production DNS framing/encoding, query scheduling, KCP, Noise, smux, BBR-lite and fair queues. Per-stream deterministic payloads and upload acknowledgments validate exact bytes, stream isolation and ordering. TLS cases perform real TLS 1.3 negotiation and certificate verification over this stack. Synthetic application exchanges are not HTTP, SOCKS negotiation or tun2socks tests.

The matrix includes capacities from 64 kbps through a configured 2 Gbps, asymmetric directions, high RTT, repeated capacity reductions, short blackouts, ordered head-of-line stalls, jitter, batched downstream feedback, small/deep finite queues, concurrent bulk/tiny requests, slow receivers, idle restart, churn, and record loss/duplication. Optional soak repeatedly transfers download/upload/tiny workloads during changing uplink capacity. `background-contention` reduces available service; it does not implement competing CUBIC flows. `ack-compression` batches DNS responses, not kernel TCP ACKs. Record-dropping cases are separately labeled: outer TCP normally repairs IP loss and exposes an ordered pause instead.

Acceptance checks require byte integrity, transfer completion within deadlines, shutdown progress, zero reliable-server response drops, and bounded carrier queues. Selected performance cases have minimum throughput and tiny-request p95 limits saved in `run.py`; these are regression thresholds, not standards or maximum-speed promises. Results retain per-transfer goodput, wire bytes, queue peaks, interactive latency, settings, logs, environment and source hashes. Race runs test concurrency correctness and must not be used to estimate production throughput.

The bare-carrier D/U/D reference omits protocol overhead and uses 16,000-byte download chunks and upload chunks of `MTU` (default 500). `--raw-only` runs this reference separately. This is a packetization-specific simulator calibration, not a physical line-rate measurement or an outer-TCP baseline: it omits kernel TCP, congestion control and reverse TCP ACK traffic. Host scheduling and timer resolution can dominate fast carriers. Earlier audit artifacts used 1,400-byte chunks in both directions; their raw fractions must not be compared directly with this calibration. A tunnel can outperform that earlier small-chunk reference because it bundles responses more efficiently.

The sandbox lacks `tc`, so no Linux netem, AQM/ECN, actual TCP CUBIC/BBR coexistence, Wi-Fi driver, route/CAKE or WAN tests are claimed. Real-host follow-up should use independent receiver-ingress netem impairments, validate direct baselines, save seeds, separate warmup/measurement, alternate direct/tunnel/direct runs, and include staggered competing flows for several minutes. See [research](../../docs/history/UPLINK_RESEARCH.md), [earlier results](../../docs/history/UPLINK_TEST_RESULTS.md), and [profiling results](../../docs/history/PROFILING_RESULTS.md). No finite matrix establishes maximum throughput on every uplink.
