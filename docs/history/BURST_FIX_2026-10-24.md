# auditfix2: preserve live TCP carriers through reply bursts

The real-device auditfix1 tests supplied two distinct outcomes:

- The ordinary shared gateway still fails its upload, then rebuilds the
  session following an OpenStream timeout. The supplied server window has
  no authentication failure, TCP write failure or queue-overflow event.
- Two separate clients on port 7001 pass probe → 5 MB download → 1 MiB upload
  → three follow-up requests, using one session each. Those passes make
  shared-session load a diagnostic target; they do not establish a cause or
  reliability rate. The WAN and server remain shared.

While extending local coverage to the actual TCP framing, an independent
reply-burst reset was reproduced. The original simulation matrix exchanged
whole DNS packets; it did not combine the framed client and server transports.

## Reproduction and fix

The minimized package test fills a carrier's bounded output queue before its
peer starts reading. On auditfix1, the next rejected reply closes the socket,
and even earlier accepted replies are lost. Both the message-count and byte
limit cases fail. A buffered framed-transport stress control also fails all
three runs with this queue policy while several TLS streams share a session.

The server now returns a temporary admission error for the single new DNS
reply that cannot fit. No part of that message has been written to the TCP
stream. Already queued replies retain their order and contents, and the live
carrier stays open. KCP handles the unsent datagram through retransmission.
The bounds remain 64 queued messages and 1 MiB including the active write.
Actual write failures, disconnections and the existing 30-second stuck-write
deadline still close the socket. The global DNS send loop does not wait for
that carrier. Repeated admission/write errors use bounded health logging as
`event=dns_reply_failed`, with counts retained in health summaries.

The regression checks both limits, drains and validates every accepted frame,
then sends another reply successfully on the same connection:

```sh
go test -race ./dnstt-server -run TestReplyQueueBurstDoesNotCloseLiveCarrier -count=3
```

The full nine-package suite passes normally and with the race detector;
`go vet ./...` also passes. The diagnostic buffered transport uses a 1 MiB
asynchronous send buffer, a 10 Mbps serialization model, 31-byte reads, real
production TCP framing and TLS application streams. Rejecting only the unsent
reply changes the three failed runs to three passing runs with exact payloads.
These models are not kernel TCP or WAN performance measurements. Logs, test
fixture source and before/after evidence are retained under
`/workspace/dnstt-audit/incident-20261024/`.

## Field status and deployment

This is a separately proven burst-reset fix. The existing field logs **do not
show its overflow event**, so it is not a proven explanation or repair of the
earlier shared-gateway upload stall. A failed-run packet capture may still be
needed to locate the DNS parse error or other carrier/protocol stall. Do not
call the shared workload fixed solely because private sessions pass.

Only server behavior changes in auditfix2. The client build stamp is updated
for release identification; an existing auditfix1 client is wire compatible.
For the next comparison, replace the VPS server with the auditfix2 ARM64
binary, retain the current gateway flags and client, restart the server and
gateway, then run the existing quick benchmark. Keep both successful private
runs and all failed shared runs as separate evidence.
